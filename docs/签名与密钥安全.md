# 道枢罗盘 · 签名与密钥安全

> 对应原始需求文档第 2、3 节。核心原则：**签名密钥只存在于本地与 GitHub Secrets，仓库内绝不出现任何密钥内容**（不使用 `key.properties`，不硬编码密码）。
> 相关文件：`app/build.gradle.kts`、`.gitignore`、`.github/workflows/build-apk.yml`、`scripts/generate-keystore.sh`、`scripts/encode-keystore.sh`、`scripts/verify-apk.sh`、`keystore/README.md`。

---

## 一、签名配置读取关系（唯一事实来源：`app/build.gradle.kts`）

```text
环境变量（本地 / CI 注入）
  KEYSTORE_PATH              已解码 keystore 的绝对路径（可选，优先于 base64）
  ANDROID_KEY_ALIAS          密钥别名
  ANDROID_KEY_PASSWORD       key 密码
  ANDROID_STORE_PASSWORD     keystore 密码
        │
        ▼
hasReleaseSigning = KEYSTORE_PATH != null && ALIAS != null && KEY_PASSWORD != null && STORE_PASSWORD != null
        │
        ├─ true  → signingConfigs.release（声明并产出 v1 + v2 + v3，v4 关闭）
        └─ false → release 变体回退 signingConfigs.debug（本地开发也能出包）
```

| 项目 | 取值 | 位置 |
|------|------|------|
| keystore 回退查找 | `KEYSTORE_PATH` 为空时尝试 `rootProject.file("release-key.jks")` | `app/build.gradle.kts` |
| 签名方案开关 | `enableV1Signing = true`、`enableV2Signing = true`、`enableV3Signing = true`、`enableV4Signing = false` | 同上 |
| 签名方案**实际产出** | **v1 + v2 + v3 三种签名均写入产物**（v1：`META-INF/MANIFEST.MF|CERT.SF|CERT.RSA`；v2/v3：APK Signing Block 内 `0x7109871a`/`0xf05368c0`）；`apksigner` 默认区间（30..35）只把 **v3** 记为 `true`，这是**上报口径**而非缺失，细则见第六节 | 同上 + 实测 |
| 是否使用 `key.properties` | **否**（需求明确要求，改用环境变量） | 同上 |
| CI 解码位置 | `$RUNNER_TEMP/release-key.jks`（`chmod 600`） | `.github/workflows/build-apk.yml` |

## 二、本地生成 keystore

```bash
keytool -genkey -v \
  -keystore release-key.jks \
  -storetype JKS \
  -keyalg RSA \
  -keysize 2048 \
  -validity 10000 \
  -alias daoshu-compass
```

交互式会询问：keystore 密码、key 密码、姓名与组织（DN）、城市、省份、国家代码。
建议：**keystore 密码与 key 密码不同**，并保存到密码管理器。

也可用脚本（`scripts/generate-keystore.sh`）：生成 `release-key.jks` 后直接输出 base64 与 Secrets 配置指引。

生成的 keystore 关键信息核对：

```bash
keytool -list -v -keystore release-key.jks -alias daoshu-compass
```

| 期望项 | 值 |
|--------|----|
| Keystore type | `JKS` |
| 算法 | `RSA 2048` |
| 有效期 | 10000 天（约 27 年，覆盖应用长期更新需要） |
| 别名 | `daoshu-compass` |
| 指纹 | `SHA1` / `SHA256` 指纹需记录归档（用于日后核对签名一致性） |

## 三、Base64 编码

```bash
# Linux / macOS / Git Bash
base64 -w 0 release-key.jks > release-key.jks.base64
```

```powershell
# Windows PowerShell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("release-key.jks")) | Set-Content -NoNewline release-key.jks.base64
```

```bash
# 使用脚本（推荐，输出单行便于粘贴）
bash scripts/encode-keystore.sh release-key.jks
```

> 注意：**必须单行**（无换行）。含换行的 base64 在 CI 中 `base64 -d` 会解码失败或产出损坏文件。

## 四、GitHub Secrets 配置

路径：仓库 **Settings → Secrets and variables → Actions → New repository secret**。

| Secret 名称 | 取值 | 用途 |
|-------------|------|------|
| `ANDROID_KEYSTORE_BASE64` | `release-key.jks` 的单行 base64 | CI 中解码为 `$RUNNER_TEMP/release-key.jks` |
| `ANDROID_KEY_ALIAS` | `daoshu-compass` | 传给 `ANDROID_KEY_ALIAS` |
| `ANDROID_KEY_PASSWORD` | key 密码 | 传给 `ANDROID_KEY_PASSWORD` |
| `ANDROID_STORE_PASSWORD` | keystore 密码 | 传给 `ANDROID_STORE_PASSWORD` |

CI 中的解码与注入（`.github/workflows/build-apk.yml`，Secret 走 `env` 而非命令行插值）：

```yaml
- name: 解码签名密钥到 RUNNER_TEMP（日志不打印任何密钥内容）
  env:
    ANDROID_KEYSTORE_BASE64: ${{ secrets.ANDROID_KEYSTORE_BASE64 }}
    ANDROID_KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
    ANDROID_KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
    ANDROID_STORE_PASSWORD: ${{ secrets.ANDROID_STORE_PASSWORD }}
  run: |
    set -euo pipefail
    # 逐个校验 Secret 非空（缺失直接失败，避免静默回退 debug 签名）
    keystore_path="$RUNNER_TEMP/release-key.jks"
    umask 077
    printf '%s' "$ANDROID_KEYSTORE_BASE64" | base64 --decode > "$keystore_path"
    chmod 600 "$keystore_path"
    file "$keystore_path"                       # 只输出类型与字节数，不输出内容
    echo "KEYSTORE_PATH=$keystore_path" >> "$GITHUB_ENV"
```

```yaml
- name: 构建签名 Release APK（assembleRelease）
  env:
    KEYSTORE_PATH: ${{ runner.temp }}/release-key.jks
    ANDROID_KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
    ANDROID_KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
    ANDROID_STORE_PASSWORD: ${{ secrets.ANDROID_STORE_PASSWORD }}
  run: ./gradlew assembleRelease --stacktrace
```

安全要求：

1. Secrets 通过 `env` 传递，**不得**出现在 `run:` 命令行里（避免被 shell 日志回显）。
2. 工作流任何步骤都不得 `echo` 密码或 base64 内容。
3. `release-key.jks` 只写入 `$RUNNER_TEMP`（每次运行后由 runner 清理），不写入工作区。
4. GitHub 会对含 Secret 的日志自动打码，但不应依赖该机制。

## 五、本地带签名构建

```powershell
# Windows PowerShell
$env:KEYSTORE_PATH = "E:\keys\release-key.jks"
$env:ANDROID_KEY_ALIAS = "daoshu-compass"
$env:ANDROID_KEY_PASSWORD = "<key 密码>"
$env:ANDROID_STORE_PASSWORD = "<store 密码>"
cd daoshu-compass
.\gradlew.bat assembleRelease
```

```bash
# macOS / Linux
export KEYSTORE_PATH="$HOME/keys/release-key.jks"
export ANDROID_KEY_ALIAS="daoshu-compass"
export ANDROID_KEY_PASSWORD="<key 密码>"
export ANDROID_STORE_PASSWORD="<store 密码>"
./gradlew assembleRelease
```

产物：`app/build/outputs/apk/release/app-release.apk`。

未设置环境变量时 release 变体会用 debug 签名，**这种包不能用于分发**（无法覆盖安装正式版本，也无法在后续版本中延续签名）。

## 六、签名验证

```bash
# Android SDK build-tools 中的 apksigner（需在 PATH，或用绝对路径）
apksigner verify --verbose app/build/outputs/apk/release/app-release.apk
```

路径探测（`scripts/verify-apk.sh` 的逻辑）：优先 `PATH` 中的 `apksigner`，找不到时在 `$ANDROID_HOME` / `$ANDROID_SDK_ROOT` 的 `build-tools/*/apksigner` 中按版本倒序选取，Windows 下为 `apksigner.bat`。

### 6.1 本工程实测结果（Temurin 17.0.20.1 + build-tools 35.0.0，docs-dev 与 lead 各自复现）

**关键前提：`apksigner verify` 的 v1/v2/v3 三行不是「产物包含哪些签名」的清单，而是「按本次查询的 SDK 区间实际选用哪个（范围允许内最强的）方案完成校验」的结果。** 产物内三种签名可以同时存在，但查询区间只会选中其中一个（`X-Android-APK-Signed: 2, 3` 会让弱方案在强方案可用时被跳过）。

对**同一个** `app/build/outputs/apk/release/app-release.apk`（3,143,136 字节），只改查询区间：

```text
apksigner verify --verbose --min-sdk-version 23 --max-sdk-version 23  → v1=true,  v2=false, v3=false   (exit=0)
apksigner verify --verbose --min-sdk-version 24 --max-sdk-version 27  → v1=false, v2=true,  v3=false   (exit=0)
apksigner verify --verbose --min-sdk-version 28 --max-sdk-version 29  → v1=false, v2=false, v3=true    (exit=0)
apksigner verify --verbose --min-sdk-version 30 --max-sdk-version 35  → v1=false, v2=false, v3=true    (exit=0)  ← 默认区间（minSdk 30 / targetSdk 35）
```

产物**确实同时含三种签名**（直接解析实物）：

```text
# v1（JAR 签名材料，zip 内）
META-INF/MANIFEST.MF    存在
META-INF/CERT.SF        存在   （头部：Created-By: Android Gradle 8.7.3 / Built-By: Signflinger / X-Android-APK-Signed: 2, 3）
META-INF/CERT.RSA       存在

# v2 + v3（APK Signing Block 解析，"APK Sig Block 42"）
EOCD offset            = 3143114
CentralDir offset      = 3115257
SigningBlock size(hdr) = 12280 / (ftr) = 12280
SigningBlock offset    = 3102969
  id=0x7109871a  value_len=1564B  -> v2 (APK Signature Scheme v2)
  id=0xf05368c0  value_len=1564B  -> v3 (APK Signature Scheme v3)
  id=0x504b4453  value_len=7181B  -> SourceStamp
  id=0x42726577  value_len=1899B  -> verity padding
```

**结论与正确表述**：

- **v1 + v2 + v3 三种签名均已写入产物**；`enableV1Signing/enableV2Signing/enableV3Signing = true` 的**声明有效且生效**，`enableV4Signing = false`（v4 未产出，`v3.1` 亦为 false）；
- 默认区间（30..35）下 `apksigner verify --verbose` 只把 **v3** 记为 `true`，**`v1`/`v2` 显示 `false` 属正常上报口径，并非缺失**；
- **Android 11–15 由 v3 覆盖**（v2/v3 属现代签名方案；v1 面向 API 24 以下，本工程 minSdk 30 不会用到，但仍在产物内以保证兼容性）；
- **判定标准**：`apksigner` **exit code = 0** 且输出含 `Verifies`，并且 **v2 或 v3 至少一项为 `true`**（`scripts/verify-apk.sh` 已按此断言）。

| 输出项（默认区间 30..35） | 实测值 | 说明 |
|--------|--------|------|
| `Verifies` | 出现 | 签名校验总体通过（exit=0） |
| `Verified using v1 scheme` | `false` | **仅表示默认区间不选用 v1**；v1 材料在产物内存在（`--min/max 23..23` 时为 `true`） |
| `Verified using v2 scheme` | `false` | **仅表示该区间不选用 v2**；签名块内 `0x7109871a` 存在（`24..27` 时为 `true`） |
| `Verified using v3 scheme` | **`true`** | 默认区间实际选用的方案（28..35 均为 true） |
| `Verified using v3.1 / v4 scheme` | `false` | 未产出（v4 显式关闭） |
| `Number of signers` | `1` | 单签名 |
| `Signer #1 key algorithm` / `key size` | `RSA` / `2048` | 与 keytool 生成参数一致 |
| `Signer #1 certificate DN` | `CN=DaoShu Compass Test, OU=Local Verify, O=DSH, L=Local, ST=Local, C=CN` | **本地产物用的是本地测试密钥**（仓库根目录 `release-key.jks`），正式发布的 DN 必须以 Secrets 中的密钥为准 |

> ✅ `scripts/verify-apk.sh` 已改为「**v2 或 v3 至少一项为 true**」的断言（并修掉了 Windows + Git Bash 下含空格路径传给 `apksigner.bat` 丢引号的缺陷：检测到 `.bat` 且旁有 `lib/apksigner.jar` 时改用 `java -jar` 调用），本工程产物实测 `exit=0` 通过，纯 v1 包会被正确拦截。
>
> ⚠️ 上表 v1/v2 的 `false` 曾被误读为「产物缺少 v1/v2 签名」；正确理解见本节开头的区间对照。校验时**不要只看单独一行**，要同时给区间或直接看 exit code。

其他核对方式：

```bash
# 查看证书指纹（与归档指纹比对，确认“同一把密钥”）
keytool -printcert -jarfile app/build/outputs/apk/release/app-release.apk
```

```bash
# 区间对照（同一产物，四个区间各跑一次，可复现本节的结论）
apksigner verify --verbose --min-sdk-version 23 --max-sdk-version 23 app-release.apk
apksigner verify --verbose --min-sdk-version 24 --max-sdk-version 27 app-release.apk
apksigner verify --verbose --min-sdk-version 28 --max-sdk-version 29 app-release.apk
apksigner verify --verbose --min-sdk-version 30 --max-sdk-version 35 app-release.apk
```

```powershell
# Windows 下若 apksigner 未加入 PATH
& "$env:LOCALAPPDATA\Android\Sdk\build-tools\35.0.0\apksigner.bat" verify --verbose app\build\outputs\apk\release\app-release.apk
```

## 七、绝不提交密钥：` .gitignore` 规则

必须被忽略（仓库当前 ` .gitignore` 已覆盖；可在本地核对）：

```gitignore
# 密钥与签名材料
*.jks
*.keystore
release-key.jks
key.properties
keystore.properties
*.p12
*.pfx
*.pem

# 本地环境配置
local.properties
sdk.properties

# Gradle 与构建产物
.gradle/
build/
*.apk
*.aab
*.ap_
dist/

# IDE / 系统
.idea/
*.iml
.vscode/
.DS_Store
Thumbs.db
```

> 建议补充：base64 导出文件（如 `release-key.jks.base64`）也属于密钥材料，导出后请立即删除，或自行在本地 `git exclude` 中忽略。

`keystore/` 目录只保留 `README.md`（与占位文件 `.gitkeep`），不得放入任何密钥文件。

提交前自检：

```bash
git status --short
git check-ignore -v release-key.jks local.properties key.properties

# 全仓库搜索敏感串（应在源码/配置中无命中）
git grep -n -I -E "storePassword|keyPassword|\.jks" -- . ":(exclude)docs/**" ":(exclude)README.md" ":(exclude)CONTRACT.md"
```

> 若密钥已误提交：立即视为泄露 → 更换新密钥并发布新的 applicationId（见第八节），同时用 `git filter-repo` / BFG 清理历史并强推（需与协作者协同）。

## 八、密钥丢失与轮换风险

| 风险场景 | 后果 | 应对 |
|----------|------|------|
| keystore 或密码丢失 | **无法再发布可覆盖安装的更新**（Android 要求同签名才能升级） | 多副本离线备份（加密磁盘 / 密码管理器 / 纸质保险箱），并归档 SHA-256 指纹 |
| keystore 泄露 | 他人可冒充签名发布恶意包 | 立即轮换：更换密钥 + 新 applicationId（如 `com.daoshu.compass.v2`）发布新应用；旧版本在 `release/version.json` 中提高 `minSupportedVersion` 推动迁移 |
| Secret 泄露 | CI 可被利用签名 | 立即在 GitHub 删除并重建 Secrets；轮换密钥 |
| 证书过期 | `validity` 到期后无法继续更新 | 本工程有效期 10000 天；到期前需按上一行“轮换”流程处理 |
| 长期未使用导致遗忘别名 | 构建报 `Alias <name> does not exist` | `keytool -list -keystore release-key.jks` 查看别名，与 `ANDROID_KEY_ALIAS` 对齐 |

**备份清单（一次配置长期有效）**：

- [ ] `release-key.jks` 至少 2 份离线备份（不同物理位置）。
- [ ] keystore 密码、key 密码、别名记录在密码管理器。
- [ ] `keytool -list -v` 的 SHA1 / SHA256 指纹截图或文本归档。
- [ ] GitHub 4 个 Secrets 配置完成并做过一次成功构建验证。

## 九、安全检查清单

- [ ] `app/build.gradle.kts` 中无任何明文密码、keystore 内容、base64 串。
- [ ] 仓库内无 `*.jks` / `*.keystore` / `key.properties` 文件；`keystore/` 仅有 `README.md`。注意：本地构建可能在仓库根目录留下 `release-key.jks`（测试密钥，已被 `.gitignore` 排除），**确认其未被 `git add`**。
- [ ] `.gitignore` 覆盖 `*.jks`、`*.keystore`、`key.properties`、`release-key.jks`、`local.properties`。
- [ ] 工作流日志中无密码、无 base64 内容（步骤用 `env` 传参，不打印）。
- [ ] CI 中 keystore 写入 `$RUNNER_TEMP` 并 `chmod 600`。
- [ ] `apksigner verify --verbose` 输出含 `Verifies`、**exit code = 0**，且 **v2 或 v3 至少一项为 `true`**（默认区间 30..35 通常只显示 v3 = true，v1/v2 显示 false 是上报口径而非缺失，见 6.1；如需确认三种签名都在产物内，用 6.1 的区间对照命令）；发布包签名者 DN 必须与 Secrets 中正式密钥一致（本地产物可能用本地测试密钥）。
- [ ] `scripts/verify-apk.sh` 断言为「v2 或 v3 至少一项为 true」，本工程产物跑出 `exit=0`。
- [ ] 发布产物的签名指纹与上次发布一致（同一把密钥）。
- [ ] 发布完成后 Secrets 与本地备份状态无变化（未被误改）。
