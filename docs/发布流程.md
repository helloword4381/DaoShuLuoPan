# 道枢罗盘 · 端到端发布流程

> 对应原始需求文档第 2、3、6 节。本文覆盖：首次一次性配置 → 日常发布 → 版本号策略 → 回滚 → 验证清单。
> 相关文件：`.github/workflows/build-apk.yml`、`scripts/generate-keystore.sh`、`scripts/encode-keystore.sh`、`scripts/verify-apk.sh`、`scripts/tag-release.sh`、`release/version.json`、`app/build.gradle.kts`。

---

## 一、总览：一次发布都发生了什么

```text
开发者改版本号 + version.json
        │
        └─ git commit && git push（main）
                │
                ▼
GitHub Actions: .github/workflows/build-apk.yml
  1. checkout → JDK 17 → Android SDK 35
  2. 解码 keystore（ANDROID_KEYSTORE_BASE64 → $RUNNER_TEMP/release-key.jks）
  3. ./gradlew assembleRelease（注入 KEYSTORE_PATH / ALIAS / 两个密码）
  4. apksigner verify --verbose 校验签名（产出含 v1+v2+v3；默认区间只上报 v3 = true，属口径而非缺失）
  5. 生成交付物：道枢罗盘-v{versionName}.apk + daoshu-compass-v{versionName}.apk + SHA256SUMS.txt
  6. 上传 workflow artifact
  7. 生成 release/version.json，并仅在 tag v* 触发时回推 main（rebase 后推送，失败不中断构建）
  8. tag v* 触发时创建 GitHub Release 并附加 ASCII 名 APK
                │
                ▼
用户端：App 检查三级通道 → 发现新版本 → 下载 → FileProvider 安装
```

## 二、首次配置（一次性）

### 2.1 生成签名密钥

```bash
# 在仓库根目录之外的安全位置执行（不要放在仓库内）
keytool -genkey -v \
  -keystore release-key.jks \
  -storetype JKS \
  -keyalg RSA \
  -keysize 2048 \
  -validity 10000 \
  -alias daoshu-compass
```

Windows PowerShell 下同样可用：

```powershell
keytool -genkey -v -keystore release-key.jks -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias daoshu-compass
```

如需交互式引导（含密码与 DN 信息自动生成），可使用 `scripts/generate-keystore.sh`。
别名固定建议为 **`daoshu-compass`**，后续与 Secret `ANDROID_KEY_ALIAS` 保持一致。

### 2.2 编码为 Base64

```bash
# Linux / macOS / Git Bash
base64 -w 0 release-key.jks > release-key.jks.base64
```

```powershell
# Windows PowerShell（输出单行，便于直接粘贴）
[Convert]::ToBase64String([IO.File]::ReadAllBytes("release-key.jks")) | Set-Content -NoNewline release-key.jks.base64
```

也可直接使用 `scripts/encode-keystore.sh`（输出单行 base64）。

### 2.3 配置 4 个 GitHub Secrets

仓库页面：**Settings → Secrets and variables → Actions → New repository secret**

| Secret 名称 | 内容 | 对应的构建环境变量 |
|-------------|------|-------------------|
| `ANDROID_KEYSTORE_BASE64` | 上一步得到的单行 base64 文本 | CI 中解码为 `KEYSTORE_PATH` 指向的 `.jks` |
| `ANDROID_KEY_ALIAS` | 密钥别名，如 `daoshu-compass` | `ANDROID_KEY_ALIAS` |
| `ANDROID_KEY_PASSWORD` | key 密码 | `ANDROID_KEY_PASSWORD` |
| `ANDROID_STORE_PASSWORD` | keystore 密码 | `ANDROID_STORE_PASSWORD` |

> 安全要求：Secret 名称与上文完全一致（工作流按名读取）；**不要在日志、脚本参数、提交信息中打印 Secret 内容**。详见 [签名与密钥安全.md](签名与密钥安全.md)。

### 2.4 初始化 `release/version.json`

仓库需在发布前包含 `release/version.json`（首次即 `versionCode = 1000` / `versionName = "1.0.0"`），字段与更新模块读取的 `VersionInfo` 严格对应：

```json
{
  "versionCode": 1000,
  "versionName": "1.0.0",
  "downloadUrl": "https://github.com/helloword4381/DaoShuLuoPan/releases/download/v1.0.0/daoshu-compass-v1.0.0.apk",
  "changelog": "首个正式版：四层罗盘表盘（360°刻度/二十八宿/六十甲子/二十四山+八卦）、传感器融合与最短路径平滑、GeomagneticField 磁偏角、DataStore 设置持久化、三级降级自动更新与 APK 安装。",
  "forceUpdate": false,
  "minSupportedVersion": 1
}
```

> 以上正是仓库当前 `release/version.json` 的内容（可 `cat release/version.json` 核对）。

字段语义与降级通道规则见 [自动更新通道.md](自动更新通道.md)。

### 2.5 首次发布自检

```bash
# 本地确认版本号与 version.json 一致
grep -E "appVersionCode|appVersionName" app/build.gradle.kts
cat release/version.json
```

## 三、日常发布

### 3.1 发布步骤

| 步骤 | 操作 | 命令 / 位置 |
|------|------|-------------|
| 1 | 提升版本号 | 编辑 `app/build.gradle.kts` 的 `appVersionCode` / `appVersionName` |
| 2 | 同步更新描述 | 编辑 `release/version.json` 的 `versionCode` / `versionName` / `downloadUrl`（`changelog` 会在 CI 中按固定文案重新生成，见下方说明） |
| 3 | 提交并推送 | `git add . && git commit -m "release: v1.0.1" && git push` |
| 4 | 自动构建 | Actions 触发 `build-apk.yml`，构建签名 APK、校验签名、生成交付物与 `SHA256SUMS.txt`，上传 artifact |
| 5 | 回推 version.json | **仅在 tag `v*` 触发时**：CI 先按 `app/build.gradle.kts` 重新生成 `release/version.json`，再 `git fetch` + `git rebase` 后推送回 `main`（提交信息含 `[skip ci]`；`continue-on-error: true`，fetch/rebase/push 任一失败只告警、不中断构建） |
| 6 | 创建 Release | tag `v*` 触发时用 `softprops/action-gh-release@v2` 创建 GitHub Release（`make_latest: true`），仅附加 ASCII 名资产 `daoshu-compass-v{versionName}.apk` |

> `release/version.json` 的权威生成方是 CI：tag 构建时按 `app/build.gradle.kts` 的 `appVersionName` / `appVersionCode` 与仓库 owner/repo **重新生成**（`changelog` 由 CI 固定文案给出，`forceUpdate = false`、`minSupportedVersion = 1`）。人工编辑该文件主要用于：非 tag 流程预览、回滚场景（见第五节）、以及通过 `version-check.yml` 的 PR 校验。

### 3.2 触发方式

`.github/workflows/build-apk.yml` 支持三种触发：

| 触发 | 说明 |
|------|------|
| `push` 到 `main`（路径过滤） | 仅当 `app/**`、`build.gradle.kts`、`settings.gradle.kts`、`gradle/**`、工作流自身变更时才构建，纯文档改动不触发 |
| `workflow_dispatch` | 手动触发，可选输入 `versionName` / `versionCode` 覆盖（**只改写 CI 临时检出内的 `app/build.gradle.kts`，绝不提交**） |
| `push` tag `v*` | 构建并创建 GitHub Release、附加 APK（GitHub 不对标签推送评估 `paths` 过滤） |

> 并发控制：`concurrency.group = build-apk-${{ github.ref }}`（`cancel-in-progress: false`），避免同一 ref 两个运行同时回推 `version.json`。权限：`contents: write`。
>
> 另有 `.github/workflows/version-check.yml`：针对 `app/build.gradle.kts` / `release/version.json` 的 PR 或手动触发，校验 JSON 合法、字段恰为 6 个、`versionName` / `versionCode` 与构建脚本一致、`downloadUrl` 指向 `v{versionName}/daoshu-compass-v{versionName}.apk`。

### 3.3 手动打 tag

```bash
# 读取 app/build.gradle.kts 中的 appVersionName，创建注解标签 v{versionName} 并推送
bash scripts/tag-release.sh --dry-run     # 先演练，只打印将要执行的 git 命令
bash scripts/tag-release.sh               # 交互确认后打标签并推送
bash scripts/tag-release.sh --yes -m "首个正式版"   # 跳过确认（自动化用）
```

脚本行为（`scripts/tag-release.sh`）：

- 从 `app/build.gradle.kts` 解析 `appVersionName`（回退 `versionName`）与 `appVersionCode`；
- 要求工作区已提交、标签不存在，否则报错退出；
- 创建**注解标签** `v{versionName}`（默认说明 `道枢罗盘 v{versionName}（versionCode {versionCode}）`）并 `git push <remote> <tag>`；
- 推送成功后提示 CI 将执行 `.github/workflows/build-apk.yml`。

手工等价命令（不依赖脚本）：

```bash
VERSION=$(grep -oP 'appVersionName\s*=\s*"\K[^"]+' app/build.gradle.kts)
git tag -a "v$VERSION" -m "道枢罗盘 v$VERSION"
git push origin "v$VERSION"
```

发布后在 CI/本地执行签名校验：

```bash
bash scripts/verify-apk.sh app/build/outputs/apk/release/app-release.apk
```

> 判定口径以 [签名与密钥安全.md](签名与密钥安全.md) 6.1 为准：本工程产物**同时含 v1 + v2 + v3 三种签名**（v1 材料在 `META-INF/`，v2/v3 在 APK Signing Block），而 `apksigner verify --verbose` 的三行是「按查询 SDK 区间选用哪个方案校验」的上报结果——默认区间（30..35）只显示 **v3 = true**，v1/v2 显示 false **并非缺失**。正确断言是「**exit code = 0 且 v2 或 v3 至少一项为 true**」。`scripts/verify-apk.sh` 已按此更新，并修掉了 Windows + Git Bash 下含空格路径传给 `apksigner.bat` 丢引号的缺陷（改用 `java -jar lib/apksigner.jar`）。

### 3.4 构建产物命名

| 文件名 | 生成方式 | 用途 |
|--------|----------|------|
| `dist/道枢罗盘-v{versionName}.apk` | CI 由 `app-release.apk` 复制重命名 | 中文名便于人工分发（随 artifact 上传，不进 Release） |
| `dist/daoshu-compass-v{versionName}.apk` | 同上 | ASCII 名；GitHub Release 资产，`version.json` 的 `downloadUrl` 指向它 |
| `dist/SHA256SUMS.txt` | `sha256sum ./*.apk` | 校验和，随 artifact 上传并写入 Release 说明 |

Actions artifact 名称：`daoshu-compass-v{versionName}-release`（保留 30 天，包含上述三个文件）。

## 四、版本号策略

| 字段 | 位置 | 规则 |
|------|------|------|
| `versionCode` | `app/build.gradle.kts` → `appVersionCode` | 单调递增整数，**每次发布必须 +1**，禁止回退；当前为 `1000` |
| `versionName` | `app/build.gradle.kts` → `appVersionName` | 语义化版本 `主.次.修订`，当前 `1.0.0` |
| Git tag | 仓库 tag | `v{versionName}`，例如 `v1.0.0` |
| `release/version.json` | `release/version.json` | `versionCode` / `versionName` 必须与 `app/build.gradle.kts` 完全一致 |

约定：

- 新增功能 → 次版本号 +1（`1.0.0` → `1.1.0`）。
- 仅修复缺陷 → 修订号 +1（`1.1.0` → `1.1.1`）。
- 破坏性变更 / 强制升级 → 提升 `minSupportedVersion` 并置 `forceUpdate = true`：低于该 `versionCode` 的客户端会被强制更新（`isForceUpdate` 同时考虑远端 `forceUpdate` 与 `minSupportedVersion`，见 `DefaultUpdateRepository.isForceUpdate`）。

**版本号与 `versionCode` 的换算必须保持一致**：通道 3（GitHub Releases API）无法从 `version.json` 取 `versionCode`，只能由 tag 推断，算法（`DefaultUpdateRepository.inferVersionCodeFromTag`）为：

```text
tag = v1.0.1      →  major=1, minor=0, patch=1  →  versionCode = 1*1000 + 0*10 + 1 = 1001
tag = v1.1.0      →  versionCode = 1*1000 + 1*10 + 0 = 1010
tag = v1.2.3      →  versionCode = 1*1000 + 2*10 + 3 = 1023
tag 不含数字      →  回退 1000
```

因此推荐 **`versionCode = major*1000 + minor*10 + patch`**（当前 `1.0.0` → `1000`）。若自定义 `versionCode` 与 tag 不对应，通道 1/2 仍按 `version.json` 判断（准确），仅通道 3 的降级场景可能误判。

> 通道 3 的两个限制（已在代码中注释）：Releases API 不返回 `forceUpdate` / `minSupportedVersion`，组装时固定为 `false` / `1`；`versionName` 取 `tag_name` 去掉 `v` 前缀，为空时用 `unknown`。也就是说**强制升级只在通道 1/2 可用时生效**。

## 五、回滚

### 5.1 场景 A：新版本已发布但有问题，需让客户端回到旧版本

1. 在 **GitHub → Releases** 中把上一个稳定版本标记为 `latest`（编辑 Release 勾选 “Set as the latest release”），或删除/转为草稿有问题的 Release。
2. 修改 `release/version.json`，把 `downloadUrl` 指回旧版本 APK，并把 `versionCode` / `versionName` 改为旧版本的值：

```json
{
  "versionCode": 1000,
  "versionName": "1.0.0",
  "downloadUrl": "https://github.com/helloword4381/DaoShuLuoPan/releases/download/v1.0.0/daoshu-compass-v1.0.0.apk",
  "changelog": "回滚至 1.0.0：修复 1.0.1 的启动闪退问题。",
  "forceUpdate": true,
  "minSupportedVersion": 1000
}
```

3. 提交并推送 `release/version.json`（如只需修数据、无需重新打包，可只改该文件）。

> 注意：Android 不允许降级安装（`versionCode` 低于已安装版本会被系统拒绝）。客户端回滚的正确做法是**发布一个 versionCode 更高、但代码回到旧状态**的版本**（例如 `1.0.2` / `versionCode 1002`），把 `downloadUrl` 指向该新构建的 APK，而不是把 `versionCode` 改回小值。

### 5.2 场景 B：工作流或构建问题，需停止分发

1. 删除或撤回（转为草稿）有问题的 GitHub Release，避免客户端解析到错误 `downloadUrl`。
2. 把 `release/version.json` 的 `versionCode` 回退到线上稳定版数值，使三级通道对客户端返回 `UpToDate`。
3. 若自动回推 `version.json` 的步骤已把错误数据推到 `main`，直接 `git revert` 对应提交（提交信息含 `[skip ci]`，不会触发构建）。

### 5.3 场景 C：密钥泄露或需轮换签名密钥

Android 不允许更换签名的 APK 覆盖安装，只能更换 applicationId（例如新增 `.v2` 后缀）发布新应用，或通过 Play App Signing 的上传密钥轮换流程；见 [签名与密钥安全.md](签名与密钥安全.md) 第五节。

## 七、常见失败与处置

| 失败点 | 现象 | 处置 |
|--------|------|------|
| keystore 解码 | `KEYSTORE_PATH` 文件不存在 / `Keystore was tampered with` | 校验 `ANDROID_KEYSTORE_BASE64` 是否单行且完整；本地重新编码后覆盖 Secret |
| 签名回退 | 产物用 debug 签名（Actions 日志提示 unsigned/fallback） | 检查 4 个 Secret 是否齐全；`app/build.gradle.kts` 依据 `hasReleaseSigning` 判定 |
| version.json 回推失败 | 日志提示 push 失败但构建继续 | 多为 `main` 有保护规则或并发推送冲突；人工把 `release/version.json` 推送一次 |
| Release 未创建 | 只有 artifact | 只有 `tag v*` 触发才会创建 Release；补打 tag 或重新运行工作流 |
| 客户端检查不到更新 | 一直 `UpToDate` | 确认 `release/version.json` 已推到 `main`，且 `versionCode` 大于本地；三级通道逐个用浏览器验证，见 [自动更新通道.md](自动更新通道.md) |
